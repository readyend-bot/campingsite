# 구현 기준

2026-09-28 사용자가 코딩 시작과 토스 스타일의 단순한 화면, 빈자리·배정·장박의 색상 구분을 요청했다. 이전 구현 보류를 해제한다.

## 화면

관리실 업무용 화면. 흰색과 차가운 회색 바탕, 파란 주요 버튼, 넉넉한 여백, 읽기 쉬운 한국어 서체. 토스의 시각적 분위기를 참고한 자체 UI이며 토스 공식 구성요소나 로고를 사용하지 않는다. DESIGN_VARIANCE 3 / MOTION_INTENSITY 2 / VISUAL_DENSITY 5. 홍보 페이지용 design-taste-frontend 스킬의 랜딩 페이지 규칙은 적용하지 않는다. Radix Dialog의 접근성 동작과 기본 HTML 입력 요소를 사용한다.

자리 상태는 빈자리 초록, 배정 파랑, 장박 주황, 사용중지 회색. 색 외에 상태명과 범례를 제공한다. 왼쪽 탐색, 중앙 배치도, 오른쪽 예약 명단과 선택 정보로 구성한다. 예약 명단, 주간 캘린더, 장박, 자리 편집, 설정은 실제 동작하는 화면으로 구현한다.

## 실행 구성

React + TypeScript + Vite, Electron 22.3.27의 Windows 설치형 앱. Chrome 108 대상으로 번들링한다. Windows 8 지원을 유지하기 위해 Electron 22를 명시적으로 고정한다. Electron 22는 공급자의 보안 유지보수가 끝났으므로 새 운영체제용 기본 선택으로 권장되는 구성이 아니다. 업무 창은 외부 웹 콘텐츠 이동을 차단하고 로컬 자산과 제한된 IPC만 사용한다. 캠핏 로그인 창은 별도 세션이며 preload·파일 IPC 없이 공식 관리자 사이트만 연다. 0.1.8부터 CSV/XLSX 내보내기 기반 버튼 동기화를 지원한다. 첫 연결 후 같은 화면의 내보내기 파일을 받아 반영하며, 실제 캠핏 내보내기의 존재·규격은 Windows 설치 후 확인한다. Windows 8·8.1·10·11 실제 설치 검증은 별도이며 빌드 성공과 혼동하지 않는다.

단일 PC의 데이터는 사용자 데이터 폴더의 JSON 파일로 원자적 교체 방식으로 저장한다. 날짜별 백업은 별도 폴더에 생성하며 앱 실행 중과 다음 실행 시 누락된 백업을 보완한다. 종료 중 예약 작업 실행을 설치하는 것은 이번 버전에 포함하지 않는다. 브라우저 미리보기는 별도의 localStorage를 사용한다.

저장 파일이 없는 설치 앱은 0.1.14부터 사용자 확정 도면의 140자리·15시설을 자동 생성·저장한다. 예약·배정·장박은 빈 상태로 시작한다. 기존 저장 파일에는 도면을 자동 재적용하지 않으며 필요하면 ‘소풍캠핑장 도면 적용’으로 합친다. 가려진 번호는 사용자의 명시적 지시에 따라 연번으로 복원하고 장박은 생성하지 않는다. 기존 자리와 합칠 때 ID·예약·배정·블록을 보존하며 유형 충돌 시 변경 전체를 취소한다. 기존 도면의 갱신은 `upgradeSopungPlan`으로 처리하고 운영자가 편집한 간격·항공사진 좌표를 유지한다. 체험 데이터는 구분하고 실제 운영 전환 시 확인 후 제거한다. 레이트 시간·금액은 미설정 상태로 두고 설정 후 사용할 수 있게 한다. 시작 잠금은 앱의 첫 실행에서 PIN 또는 비밀번호를 선택하도록 한다.

`Site.detail`은 카라반 세부 유형을 저장한다. `State.facilities`에 동별 시설 위치·종류·표시 크기를 보관하며 `sitePlan`으로 제공 도면을 식별한다. 기존 version 1 백업에서 필드가 없어도 읽을 수 있다. `src/sitePlan.ts`에 원본 배치, `src/CampOverview.tsx`에 사진·도면 기준 전체 지도와 구역 선택, `src/PlanFeatures.tsx`에 시설 표시·확대, `src/AreaLayout.tsx`에 상세·편집을 구현한다. 기본 전체 화면에서 동 상세로 이동해 자리를 선택하며 손님·날짜는 유지한다. 상세 높이는 내용에 맞추고 인쇄 도면은 A4 가로 용지에 맞춰 제한한다.

예약 파일은 실제 파일을 받기 전에는 캠핏·네이버 전용 파서라고 주장하지 않는다. CSV/XLSX 열 연결과 미리보기로 읽고 원본 예약번호·단위번호로 구별한다. 날짜 변경과 취소는 별도 확인 후 반영한다. 원본에서 행이 사라졌다는 이유로 취소 처리하지 않는다.

## 검증

기간 전체 충돌, 입퇴실 시간 경계, 장박·사용중지, 이동 확인 전 출발지 유지, 취소·날짜 변경 확인, 재가져오기 멱등성과 현장 정보 보존을 자동 테스트한다. Playwright로 예약 등록·배정·색상 상태·이동·저장 후 재실행, 가져오기, 화면 크기를 검증한다. Windows 설치 파일 빌드와 실제 Windows 실행은 따로 기록한다. 실행 결과는 [README의 검증 기록](../README.md#검증-기록)에 정리했다.

2026-10-08의 0.1.12 전체 재검토에서 운영 60개·화면 38개와 Mac Electron 22 검증을 통과했다. 복원·전체 상태 교체·가져오기·백업 오류 수정과 보안 의존성의 남은 한계는 [최종 검토 기록](final-review-2026-10-08.md)에 정리했다.

## 0.1.13 변경 (2026-10-08)

[Claude 독립 검토](claude-final-review-2026-10-08.md)의 확정 오류와 사용자 결정 Q70을 반영했다.

- **입실 전 지정 객실:** `assignWaitingRoom`·`releaseWaitingRoom`(`src/domain.ts`)은 도착 전 카라반·방갈로 예약만 다룬다. 같은 숙박 유형의 사용 가능한 객실과 전체 이용 기간의 겹침을 검사하고 입실 처리는 하지 않는다. 시작하지 않은 보류 배정은 지우고, 입실일이 지난 보류는 지금까지를 이력으로 남긴다. 반복 가져오기는 기존 예약의 배정을 바꾸지 않는다.
- **날짜 경계:** `addDays`·`mondayOfWeek`는 잘못된 입력이나 네 자리 연도를 벗어난 결과에서 예외 없이 원래 값을 돌려준다. 현황 날짜는 `validDate`를 통과한 값만 쓴다. `ErrorBoundary`(`src/components.tsx`)가 예상하지 못한 화면 오류에 다시 불러오기 화면을 보여 준다.
- **도면 재적용:** `applySopungPlan`은 공식 ID 자리의 동·이름·유형·세부 유형·위치를 유지하고, 이름으로 찾은 수동 자리만 도면 유형으로 맞춘다. 시설은 기존 위치·크기·정보를 유지하고 빠진 값만 채운다.
- **원본 날짜 변경:** 새 퇴실 시각이 지금 자리의 이용 시작보다 빠르거나(이동 이후 단축), 입실 손님의 새 퇴실 시각이 이미 지났으면 반영 전에 거절한다.
- **명단:** `allocationIndex`로 예약별 현재·마지막 배정을 한 번에 찾고, 예약 명단·지도 옆 명단은 100건씩 나눈다.
- **사용중지 시작 시각:** 사용중지는 시작 시각을 입력받는다(오늘은 지금, 다른 날은 0시가 기본). 장박은 기존처럼 14시 시작이다.
- **가져오기:** 같은 경로·예약번호에 새 단위번호가 들어오면 경고한다. 지정 객실은 정확히 같은 이름을 먼저 찾고, 없으면 공백만 무시한 유일한 같은 유형 객실에 배치한다.
- **저장 용량:** 저장소가 저장 크기(`bytes`)와 한도를 돌려주고, 화면은 75%부터 `storageNotice`로 계속 안내한다. 16MB 한도는 바꾸지 않았다.

### 지난 연도 보관과 첨부 파일 (Q70)

- `archiveCandidates`·`archivePlan`(`src/domain.ts`)이 올해(한국 시간) 이전에 끝난 퇴실·노쇼·취소 예약과 그 배정·변경 기록, 예약과 무관한 지난 연도 기록을 고른다. 연도별로 약 8MB 이하 파일로 나눈 `ArchiveFile`과 SHA-256·크기를 담은 `ArchiveRef` 목록을 만든다.
  - 본 파일 `State.archives`에는 목록만 남긴다.
  - 도착 전·입실·이동 예정·미확인 변경과 장박·사용중지·자리·설정은 옮기지 않는다.
- 저장소(`electron/repository.cjs`) `commitArchive`의 처리 순서:
  1. 화면 상태가 기존 보관 목록을 빠뜨리지 않았는지 확인한다.
  2. 새 파일의 내용·이름 중복·기존 보관 파일을 확인한다.
  3. `archive/`에 원자적으로 기록한다.
  4. 마지막에 본 파일을 교체한다.

  실패하면 이번 파일을 지운다. 메인 IPC는 성공 뒤 수동 백업을 한 번 만든다.
- 보관 파일과 항공사진 파일은 `attachments()`로 같은 방식으로 다룬다. 이름 규칙과 SHA-256으로 확인한다.
  - 일일·수동 백업은 본 백업을 쓰기 전에 백업 폴더의 `archive/`·`assets/` 사본을 만든다. 확인된 일일 백업이라도 사본을 매번 stat으로 확인한다. 빠진 사본은 원본을 확인해 다시 만들고, 내용이 다른 사본은 덮어쓰지 않고 오류로 알린다.
  - `fileProblems`는 상태 확인용으로 존재·크기만 본다.
- 과거 검색(`searchArchives`)과 반복 가져오기용 조회(`lookupArchives`)는 필요할 때만 보관 파일을 읽어 확인한다.
  - 검색은 한 쪽(100건)씩 `offset`으로 보낸다.
  - `importRows`는 보관된 예약을 새로 만들지 않고 차이만 경고한다.
- 백업 폴더 복원(`inspectBackup` → `restoreBackup`):
  - 확인한 백업 JSON의 SHA-256 토큰으로 묶는다. 백업 옆이나 데이터 폴더의 정상 첨부 파일을 모두 확인한다.
  - 내용이 다른 현재 첨부 파일은 `replaced-<시각>/`로 옮긴 뒤 정상 사본을 쓰고 본 파일을 교체한다.
  - 중간 실패 시 새 파일을 지우고 옮긴 파일과 본 파일을 되돌린다.
  - 보관 목록이 없는 예전 단일 백업도 같은 경로로 복원된다.
  - 파일 입력 복원은 이 PC에 같은 첨부 파일이 있을 때만 진행한다(`verifyAttachments`).
- 항공사진(`saveAerial`·`readAerial`)은 `assets/aerial-<SHA-256>.<확장자>` 불변 파일로 저장한다. 본 파일에는 `asset:` 참조만 둔다.
  - 화면은 IPC로 읽은 data URL을 표시에만 쓴다.
  - 기존 내장 사진은 같은 바이트로 옮길 수 있다.
  - 브라우저 미리보기는 기존처럼 data URL을 쓴다.
- 메인 프로세스 코드는 Electron 22의 Node 16.17 범위 API만 쓴다. 화면의 SHA-256 계산은 Chromium 108의 Web Crypto를 쓴다.
