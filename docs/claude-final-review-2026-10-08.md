## 상세

### F1 [중요] 데이터 누적으로 16MB 저장 한도에 도달하면 모든 저장 실패

- **위치**:
  - `electron/repository.cjs:44-45`: 저장 크기 16MB 초과 시 거절.
  - `src/domain.ts:218-225`: 활동 기록을 무제한 누적.
  - `src/App.tsx:2024-2034`: 항공사진 base64를 상태 JSON에 저장.
  - `electron/repository.cjs:107-118`: 일일 백업을 삭제하지 않음.
- **발생 조건**: 예약·배정·변경 기록이 계속 쌓여 저장 JSON이 16MB를 넘는 경우다. 지난 기록을 보관 파일로 옮기거나 지우는 기능이 없다.
- **재현**(`$R/r2-growth.ts`, 결과 `r2-output-10000.txt`): 가상 운영 1년(예약 10,104건)을 같은 도메인 함수로 생성했다.
  - 저장 크기는 11.84MB였다. 예약 1건마다 예약·배정·기록 3건이 쌓여 평균 **1,229바이트**가 늘었다.
  - 16MB를 넘긴 상태를 실제 `Repository.save`에 넣으면 `저장 파일이 너무 커요.`로 거절된다.
- **도달 시점(추정)**: 16MB에 해당하는 예약 수는 항공사진이 없으면 약 13,650건, 4MB 사진이 있으면 약 9,100건이다.

  | 연간 예약 수 가정 | 항공사진 없음 | 4MB 항공사진 |
  |---|---|---|
  | 5,000건 | 약 2.7년 | 약 1.8년 |
  | 10,000건 | 약 1.4년 | 약 0.9년 |
  | 15,000건 | 약 0.9년 | 약 0.6년 |

  실제 연간 예약 건수와 메모 길이는 확인하지 않았다. 하루 여러 번 동기화하면 기록이 더 빨리 늘어난다.
- **운영 영향**: 한도에 도달하는 순간부터 배정·입실·가져오기·설정 변경과 30초 자동 퇴실 저장이 모두 실패한다. 화면 안에는 데이터를 줄일 방법이 없어 개발자 개입이 필요하다. 성수기에 발생하면 현장 업무가 멈춘다. 데이터 10MB 기준으로 일일 백업이 연 3GB 이상 쌓인다(추정).
- **동반 지연**(같은 데이터, 이 Mac 기준):
  - 조작 1회의 복제·자동 퇴실·검증: 81ms.
  - 30초마다 하는 변경 비교: 57ms.
  - 10.6MB 저장 1회: 106ms.

  구형 Windows PC에서는 측정하지 않았다.
- **수정 제안**:
  1. 저장 크기를 설정 화면에 표시하고, 한도 75% 무렵부터 경고한다.
  2. 지난 시즌 예약·활동 기록을 연도별 보관 파일로 분리하는 보관 기능을 만든다. Q17의 과거 검색을 위해 보관 파일의 읽기 전용 검색을 함께 제공한다.
  3. 활동 기록에 상한을 두거나 요약한다.
  4. 항공사진은 상태 JSON이 아닌 별도 파일로 저장한다.
  5. 보관·백업 기간은 「결정 필요」 2번을 사용자에게 확인한 뒤 적용한다.

- **되돌리기·수정 기능 부재**: 노쇼·취소·조기 퇴실·레이트 적용을 되돌릴 수 없다. 장박의 이름·기간을 수정할 수 없고, 직접 예약의 날짜를 단축·변경할 수 없다. 실수 복구는 백업 복원뿐이다. 필요 여부는 사용자 결정 사항이다.
